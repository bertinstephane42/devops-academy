Bienvenue dans l'univers DevOps

Le DevOps est bien plus qu'un ensemble d'outils : c'est une culture qui rapproche les équipes de développement (Dev) et d'exploitation (Ops) pour livrer des logiciels de qualité plus rapidement et de manière plus fiable.

🤝

Collaboration

Fin des silos entre Dev et Ops. Les équipes partagent la responsabilité du cycle de vie complet de l'application.

⚡

Automatisation

Build, test, déploiement : tout ce qui peut être automatisé doit l'être, afin d'éliminer les erreurs manuelles et accélérer les livraisons.

📊

Mesure

Des métriques précises (MTTR, déploiements par jour, taux d'échec) guident l'amélioration continue.

🔄

Amélioration Continue

Chaque incident est une opportunité d'apprentissage. Les processus évoluent par rétroaction constante.

Bénéfices pour l'entreprise

  • Réduction du Time-to-Market – livraisons plus fréquentes et plus sûres.
  • Qualité logicielle accrue – tests automatisés et intégration continue.
  • Meilleure résilience – déploiements progressifs, rollbacks rapides.
  • Satisfaction clients – fonctionnalités livrées en continu, feedback immédiat.

Planification Plan

La planification DevOps s'appuie sur les principes Agile et Lean pour prioriser le travail, gérer les dépendances et suivre l'avancement en temps réel.

Méthodes Agiles

  • Scrum – Sprints (1–4 semaines), daily stand-ups, rétrospectives.
  • Kanban – Flux continu, limite du travail en cours (WIP), visibilité totale.
  • SAFe – Mise à l'échelle Agile pour les grandes organisations.

Outils de suivi

  • GitHub Issues / Projects – Tableaux Kanban intégrés au code.
  • Jira – Roadmaps, epic, user stories, backlog.
  • Confluence – Documentation collaborative des décisions.

📌 Le saviez-vous ?

Les équipes DevOps matures utilisent des « Service Level Objectives » (SLO) pour définir des objectifs de fiabilité dès la phase de planification.

📖 Les concepts en détail

La planification DevOps ne se limite pas à un calendrier de livraison. Elle emprunte au manifeste Agile (2001) quatre valeurs fondamentales : les individus et leurs interactions plutôt que les processus et outils, un logiciel fonctionnel plutôt qu'une documentation exhaustive, la collaboration avec le client plutôt que la négociation contractuelle, et l'adaptation au changement plutôt que le suivi d'un plan rigide.

En DevOps, la planification est continue et itérative. Contrairement au cycle en cascade (Waterfall) où tout est figé en amont, une équipe DevOps planifie par sprints (cycles de 1 à 4 semaines) avec des rétrospectives régulières qui ajustent le processus. Le Lean ajoute le concept de gaspillage : tout ce qui n'apporte pas de valeur au client (attentes, rework, documentation superflue) doit être éliminé.

⚠️ Pièges à éviter

Sprints trop longs → feedback trop tardif
Un sprint de 4 semaines retarde le retour utilisateur. En DevOps, on préfère des cycles courts (1 à 2 semaines) pour valider rapidement les hypothèses et corriger la trajectoire.
WIP illimité en Kanban → goulots d'étranglement
Sans limite de travaux en cours, les tâches s'accumulent et rien ne se termine. Fixez une limite WIP (Work In Progress) par colonne pour révéler les goulots et fluidifier le flux.
Planifier sans impliquer les ops
Si les équipes ops ne participent pas à la planification, les contraintes d'infrastructure, de sécurité et de monitoring sont ignorées. Résultat : des fonctionnalités impossibles à déployer ou à maintenir.
Rétrospectives sautées → erreurs répétées
Sans rétrospective, l'équipe reproduit les mêmes problèmes sprint après sprint. La rétrospective est le moteur de l'amélioration continue.

📚 Lexique

Sprint Cycle de développement itératif d'une durée fixe (1–4 semaines) au terme duquel un incrément potentiellement livrable est produit.
Backlog Liste ordonnée des fonctionnalités, correctifs et améliorations à réaliser, priorisée par la valeur métier.
User Story Description d'une fonctionnalité du point de vue de l'utilisateur final, format : « En tant que… je veux… afin de… ».
WIP (Work In Progress) Nombre maximum de tâches autorisées dans une colonne Kanban. Limiter le WIP révèle les goulots et améliore le flux.
Burndown Chart Graphique qui montre le travail restant dans un sprint jour après jour. Permet de visualiser si l'équipe est dans les temps.
Daily Stand-up Réunion quotidienne de 15 minutes maximum où chaque membre répond : qu'ai-je fait, que vais-je faire, quels sont les blocages.
Definition of Done Liste de critères qu'une user story doit remplir pour être considérée comme terminée (codée, testée, documentée, déployée).
Vélocité Mesure du travail qu'une équipe accomplit par sprint. Sert à prévoir la capacité future et à détecter les tendances.

💡 Exemple concret

Scénario : Une équipe de 5 développeurs utilise GitHub Projects pour planifier un sprint de 2 semaines.

  1. Le Product Owner priorise le backlog avec des user stories estimées en story points (1, 2, 3, 5, 8).
  2. Lors du sprint planning, l'équipe sélectionne les stories qu'elle s'engage à livrer, en fonction de sa vélocité historique (ex : 25 story points).
  3. Chaque matin, le Daily Stand-up de 15 min synchronise l'équipe. Le tableau Kanban dans GitHub Projects suit le flux : Backlog → Ready → In Progress → Review → Done.
  4. En milieu de sprint, un imprévu survient. L'équipe réajuste le périmètre plutôt que de reporter la date — c'est l'inspect and adapt d'Agile.
  5. En fin de sprint, la review présente le résultat au client et la rétrospective améliore le processus pour le sprint suivant.

Développement Code

Le code est le cœur du logiciel. Une gestion rigoureuse des versions et des processus de code review est indispensable.

Git & Stratégies de branching

  • Git Flow – Branches main, develop, feature/*, release/*, hotfix/*.
  • Trunk-based – Branches courtes, intégration multiple fois par jour.
  • GitHub Flow – main + branches de fonctionnalités, PR obligatoire.

Bonnes pratiques

  • Commits atomiques et messages explicites (conventional commits).
  • Code review systématique via Pull Request.
  • Protection de branche avec – vérifications obligatoires avant merge.
Exemple de conventional commit 
feat(api): ajouter le endpoint de création d'utilisateur
fix(auth): corriger le token expiré en session
docs(readme): mettre à jour les instructions d'installation

📖 Les concepts en détail

Le développement DevOps repose sur une gestion rigoureuse du code source avec Git, le système de contrôle de versions le plus utilisé. Git permet de suivre l'historique complet des modifications, de collaborer sans écrasement, et de revenir à n'importe quel état antérieur.

Les stratégies de branching sont cruciales :

  • Git Flow : le plus structuré, avec develop, feature/*, release/*, hotfix/*. Idéal pour des projets à cycle de publication fixe mais complexe à gérer.
  • GitHub Flow : minimaliste — une seule branche main et des branches de fonctionnalités. Chaque merge passe par une PR validée. Idéal pour la livraison continue.
  • Trunk-based Development : branches très courtes (moins d'un jour), intégration multiple fois par jour. Requiert une CI solide et une discipline d'équipe. C'est le modèle privilégié par Google, Netflix et Facebook.

Les conventional commits (format type(scope): message) automatisent la génération de changelog, le versionnement sémantique et le déclenchement conditionnel de pipelines CI/CD.

⚠️ Pièges à éviter

Commits trop volumineux → revert impossible
Un commit qui touche 30 fichiers est impossible à annuler proprement si un problème survient. Préférez des commits atomiques (un changement logique par commit).
PR sans review → qualité et sécurité fragiles
Une Pull Request non revue (ou mergée en solo) contourne la détection collégiale des bugs et des problèmes de conception. Exigez au moins une review approuvée avant merge.
Merge direct dans main sans PR
Pousser directement sur main supprime toute barrière de qualité. Activez la protection de branche dans GitHub pour bloquer les push directs et exiger des vérifications CI passées.
Ignorer les secrets dans le dépôt
Commiter une clé API ou un mot de passe expose l'infrastructure. Utilisez .gitignore, les secrets GitHub et des outils comme git-secrets ou truffleHog pour les détecter automatiquement.

📚 Lexique

Commit Instantané des modifications du code à un instant T, identifié par un hash SHA-1 unique, avec un message descriptif.
Branch Ligne de développement indépendante qui diverge de la branche principale pour travailler sur une fonctionnalité ou un correctif.
Pull Request (PR) Demande d'intégration d'une branche dans une autre, avec discussion, revue de code et vérifications automatisées.
Code Review Examen systématique du code par un ou plusieurs pairs avant son intégration, visant la qualité, la sécurité et la maintenabilité.
Conventional Commit Convention de message de commit structuré (type, scope, description) qui permet l'auto-génération de changelog et le versionnement sémantique automatique.
Merge Conflict Situation où Git ne peut pas fusionner automatiquement deux branches car les mêmes lignes ont été modifiées différemment.
Rebase Réécriture de l'historique qui repositionne les commits d'une branche à la suite d'une autre, offrant un historique linéaire.
Hooks (Git) Scripts déclenchés automatiquement par des événements Git (pre-commit, pre-push) pour appliquer des vérifications locales.

💡 Exemple concret

Scénario : Alice doit ajouter une fonctionnalité « réinitialisation de mot de passe » sur une application Node.js.

  1. Alice crée une branche feature/reset-password depuis main à jour.
  2. Elle code la fonctionnalité en plusieurs commits atomiques : un pour le formulaire frontend, un pour l'API backend, un pour les tests automatisés.
  3. Chaque commit suit la convention : feat(auth): ajouter le formulaire de réinitialisation.
  4. Alice pousse sa branche et ouvre une Pull Request sur GitHub.
  5. Bob, son binôme, effectue une code review et demande une modification sur la gestion des tokens.
  6. Alice corrige, pousse un nouveau commit, la PR est approuvée et mergée dans main.
  7. Après le merge, la branche de fonctionnalité est supprimée pour garder le dépôt propre.

🧪 Travaux pratiques — Forker, créer une branche et ouvrir une Pull Request

Simulez un workflow de développement collaboratif : forker un dépôt, créer une branche de fonctionnalité, pusher du code et ouvrir une PR.

  1. Forkez un dépôt public (par exemple github.com/octocat/Spoon-Knife).
  2. Clonez votre fork en local : git clone https://github.com/VOTRE-USER/Spoon-Knife.git.
  3. Créez une branche : git checkout -b feature/ma-modification.
  4. Modifiez un fichier (ex. index.html) et commitez : git add . && git commit -m "feat: ajouter ma modification".
  5. Poussez la branche : git push origin feature/ma-modification.
  6. Ouvrez une Pull Request sur GitHub → rendez-vous sur la page de votre fork : une bannière jaune propose Compare & pull request. Cliquez dessus et rédigez une description détaillée : contexte, changements, captures d'écran.
  7. Ajoutez un commentaire de review sur votre propre PR (onglet Files changed, survolez une ligne, cliquez sur le + bleu).
  8. Mergez la PR avec Squash and merge (si le bouton est grisé, cliquez d'abord sur Update branch pour mettre à jour).
  9. Après le merge, synchronisez votre dépôt local : git checkout main && git pull.

💡 Résultat attendu

Une PR mergée visible dans l'historique du dépôt, avec au moins un commentaire de review et un commit squashé. Le cycle complet forker → brancher → PR → review → merge est maîtrisé.

Intégration Continue Build & Test

L'Intégration Continue (CI) consiste à fusionner le travail des développeurs plusieurs fois par jour et à valider chaque changement par des tests automatisés.

🔍 Build automatisé

Compilation, résolution des dépendances, analyse statique (linting).

✅ Tests unitaires

Valident chaque fonction individuellement. Exécutés à chaque commit.

🧪 Tests d'intégration

Vérifient les interactions entre composants (API, base de données).

📈 Qualité du code

SonarQube, CodeQL, couverture de code – seuils de qualité bloquants.

Pratique recommandée

Chaque Pull Request doit passer une pipeline CI complète avant d'être mergée. La branche main doit toujours être déployable.

📖 Les concepts en détail

L'Intégration Continue (CI) est une pratique de développement où chaque développeur intègre son code dans le tronc commun plusieurs fois par jour. Chaque intégration est vérifiée par une compilation automatisée et une batterie de tests pour détecter les régressions le plus tôt possible.

Le concept a été popularisé par Grady Booch dans les années 1990, puis formalisé par Martin Fowler. La CI repose sur trois piliers :

  • Dépôt centralisé : tout le monde travaille sur la même base de code, partagée via Git.
  • Build automatisé : un script reproductible compile le projet, résout les dépendances et exécute les tests.
  • Feedback rapide : le développeur est notifié dans les minutes qui suivent si son code a cassé quelque chose.

Les pipelines CI modernes (GitHub Actions, GitLab CI, Jenkins) enchaînent des jobs : lint → test → build → analyse de qualité. Chaque job s'exécute dans un conteneur isolé, garantissant la reproductibilité.

En DevOps, le mantra est : « If it hurts, do it more often ». Plus les intégrations sont fréquentes, moins les conflits sont coûteux.

⚠️ Pièges à éviter

Pipeline CI qui dure plus de 15 minutes
Un feedback lent tue la CI. Optimisez le parallélisme des jobs, utilisez du caching des dépendances et fractionnez les tests longs.
Tests non déterministes (flaky tests)
Un test qui échoue une fois sur deux sans raison détruit la confiance dans la CI. Isolez les tests, supprimez les dépendances temporelles et réexécutez les tests flaky dans une CI retry limitée.
Merge sans CI passée
Si les PR peuvent être mergées malgré un pipeline rouge, la CI n'a plus de valeur. Activez la protection de branche avec « Require status checks » pour bloquer les merges non conformes.
Pipeline qui dépend de l'environnement local
« Ça marche en local ! » — si la CI utilise une config différente, le build échoue. Containerisez votre build avec Docker pour garantir la reproductibilité.

📚 Lexique

Pipeline CI Suite automatisée d'étapes (lint, test, build, analyse) exécutées à chaque push pour valider la qualité du code.
Runner Agent logiciel qui exécute les jobs d'un pipeline. GitHub fournit des runners hébergés (Ubuntu, Windows, macOS) ou on peut utiliser ses propres runners autohébergés.
Test unitaire Test qui vérifie le comportement d'une unité de code isolée (fonction, méthode, classe). Rapide et déterministe.
Test d'intégration Test qui vérifie les interactions entre plusieurs composants (API, base de données, services externes).
Code Coverage Pourcentage de code exécuté par les tests. Indicateur utile mais ne garantit pas l'absence de bugs.
Linting Analyse statique du code pour détecter les erreurs de syntaxe, les mauvaises pratiques et les incohérences de style.
Artifact Fichier produit par le build (JAR, Docker image, package npm) conservé pour les étapes avales (déploiement, publication).
Fail Fast Principe qui consiste à échouer immédiatement dès qu'une étape critique échoue, pour économiser du temps et des ressources.

💡 Exemple concret

Scénario : L'équipe Frontend utilise GitHub Actions pour valider chaque PR sur une application React.

Fichier .github/workflows/ci.yml 
name: CI
on: [push, pull_request]
jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage
      - run: npm run build
  1. Dès qu'Alice pousse sa branche feature/dark-mode, GitHub Actions déclenche la pipeline.
  2. Le job quality s'exécute sur Ubuntu : il installe les dépendances via npm ci (déterministe), exécute le linter (ESLint), lance les tests avec couverture, et vérifie que le build passe.
  3. Si tout est vert, la PR peut être mergée. Si une étape échoue, Alice reçoit une notification et corrige avant que le bug n'atteigne la branche principale.

Déploiement Continu Release & Deploy

Le Continuous Deployment (CD) automatise la mise en production de chaque changement validé par la CI, sans intervention manuelle.

Stratégies de déploiement

🟢 Blue/Green

Deux environnements identiques. Bascule instantanée du trafic de Blue (actuel) vers Green (nouveau). Rollback immédiat.

🐤 Canary

Nouvelle version déployée pour un faible % d'utilisateurs. Surveillance avant extension progressive.

🌊 Rolling update

Remplacement progressif des instances une par une (ou par lots). Aucun temps d'arrêt.

🐳 Conteneurisation

Docker empaquette l'application et ses dépendances. Image immuable, identique en dev, test et prod.

Exemple Dockerfile 
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

📖 Les concepts en détail

Le Déploiement Continu (CD) est l'étape qui suit la CI dans le pipeline DevOps. Là où la CI valide que le code est intégrable et fonctionnel, la CD déploie automatiquement ce code validé dans un environnement cible (staging, production) sans action humaine.

Il ne faut pas confondre :

  • Continuous Delivery : le code est toujours prêt à être déployé en production, mais le déclenchement du déploiement est manuel (décision métier). C'est l'approche la plus répandue dans les organisations matures.
  • Continuous Deployment : le déploiement en production est automatique dès que la CI est passée. Plus risqué, mais plus rapide. Pratiqué par Netflix, Etsy, Amazon.

Les stratégies de déploiement permettent de réduire les risques :

  • Blue/Green : deux environnements (Blue et Green) identiques. Bascule instantanée du trafic. Rollback immédiat en une seconde.
  • Canary : la nouvelle version est exposée à un petit % d'utilisateurs (ex : 5 %). Si les métriques sont bonnes, on étend progressivement à 100 %. Netflix l'utilise avec son système Spinnaker.
  • Rolling update : les instances sont remplacées une par une. Aucun temps d'arrêt, mais le rollback est plus lent.
  • Feature flags : une fonctionnalité est déployée mais désactivée. On l'active à distance sans nouveau déploiement. Outils : LaunchDarkly, Flagsmith.

La conteneurisation avec Docker est le standard moderne du CD : une image immuable (même contenu en dev, test, prod) évite les dérives de configuration.

⚠️ Pièges à éviter

Environnements non identiques → bugs de prod
Si staging et production diffèrent (OS, versions, config), ce qui marche en test peut échouer en prod. Utilisez Docker ou IaC (Infrastructure as Code) pour garantir l'identité.
Absence de rollback automatisé
Sans procédure de retour arrière, un déploiement défectueux bloque l'équipe pendant des heures. Automatisez le rollback (ex : `kubectl rollout undo` ou bascule Blue/Green inverse).
Déploiement trop rare → stress et erreurs
Déployer une fois par mois accumule des centaines de modifications : impossible de savoir ce qui a causé un incident. Plus on déploie, plus c'est sûr.
Feature flags non nettoyés
Les flags qui restent dans le code après activation définitive créent une dette technique. Supprimez le flag une fois la fonctionnalité validée par tous les utilisateurs.

💡 Exemple concret

Scénario : Une équipe déploie une application Node.js avec Docker sur un cluster Kubernetes (K8s) en stratégie Rolling update.

  1. La CI construit et pousse une image Docker taguée avec le hash du commit (registry.example.com/app:a1b2c3d).
  2. Le pipeline CD met à jour le manifeste Kubernetes (deployment.yaml) avec la nouvelle image.
  3. kubectl apply -f deployment.yaml déclenche un Rolling update : Kubernetes remplace les pods un par un tout en maintenant le service actif.
  4. Des health checks (readiness + liveness probes) valident que chaque nouveau pod est fonctionnel avant de passer au suivant.
  5. Si les probes échouent, Kubernetes stoppe automatiquement le déploiement et conserve l'état précédent — c'est un rollback automatique.

Monitoring & Feedback Observabilité

L'observabilité repose sur trois piliers : logs, métriques et traces. Elle permet de comprendre l'état interne d'un système en production.

📜 Logs

Événements textuels horodatés. Outils : ELK Stack (Elasticsearch, Logstash, Kibana), Loki, CloudWatch.

📊 Métriques

Données numériques agrégées (CPU, mémoire, requêtes/s). Outils : Prometheus, Grafana, Datadog.

🔗 Tracing

Suivi d'une requête à travers tous les services (APM). Outils : Jaeger, OpenTelemetry, New Relic.

🔄 Boucle de rétroaction

Les alertes remontent aux équipes Dev via Slack/PagerDuty. Les post-mortems alimentent le backlog d'amélioration.

📖 Les concepts en détail

Le monitoring est l'activité qui consiste à collecter, analyser et visualiser des données sur l'état d'un système en production. L'observabilité va plus loin : c'est la capacité de comprendre l'état interne d'un système à partir de ses sorties externes (logs, métriques, traces), sans avoir à ajouter du code spécifique pour chaque question.

Les trois piliers de l'observabilité :

  • Logs : événements textuels horodatés avec niveau (INFO, WARN, ERROR). Une bonne pratique est le logging structuré (JSON) pour faciliter l'indexation et la recherche. Outils : ELK Stack (Elasticsearch, Logstash, Kibana), Loki, CloudWatch.
  • Métriques : données numériques agrégées dans le temps (CPU, mémoire, taux d'erreur, latence). Les 4 golden signals de Google SRE sont : latence, trafic, erreurs, saturation. Outils : Prometheus, Grafana, Datadog.
  • Traces : suivi d'une requête à travers tous les services d'une architecture distribuée (APM). Permet d'identifier le service responsable d'une latence excessive. Outils : Jaeger, OpenTelemetry, Zipkin.

En DevOps, le monitoring boucle la rétroaction : les alertes remontent aux équipes Dev via Slack/PagerDuty, et les post-mortems sans blâme alimentent le backlog d'amélioration continue.

⚠️ Pièges à éviter

Trop d'alertes → alerte fatigue
Si tout alerte, plus rien n'est pris au sérieux. Définissez des seuils pertinents et utilisez des règles d'agrégation pour réduire le bruit. Privilégiez la qualité à la quantité.
Piloter sur des vanity metrics
Surveiller le nombre de requêtes sans regarder la latence ou le taux d'erreur donne une illusion de santé. Suivez les 4 golden signals de Google SRE.
Pas de dashboards partagés
Si chaque équipe a son outil sans visibilité croisée, les incidents sont traités en silo. Centralisez dans un Grafana commun avec des dashboards consultables par toutes les équipes.
Post-mortems avec recherche de coupable
Une culture du blâme pousse les équipes à cacher les erreurs. Les post-mortems doivent être sans blame et orientés vers l'amélioration du système, pas vers la punition.

  4. L'ingénieur de garde reçoit la notification, consulte le dashboard Grafana, identifie que le microservice payments est le goulet, et ouvre une issue GitHub prioritaire.
  5. Après le correctif, un post-mortem documente l'incident, la cause racine et les actions pour éviter la récidive.

Infrastructure as Code Terraform & Co.

L'Infrastructure as Code (IaC) consiste à gérer et provisionner l'infrastructure (serveurs, réseaux, bases de données) via du code déclaratif ou impératif, plutôt que par des actions manuelles ou des scripts ponctuels.

Déclaratif vs Impératif

  • Impératif — on décrit comment faire (Ansible, Bash, CloudFormation en mode script). Ordre des opérations explicite.
  • Déclaratif — on décrit quoi (Terraform, Pulumi, CloudFormation en mode infrastructure). L'outil calcule le plan d'exécution.

Principes clés

  • Idempotence — appliquer deux fois le même code produit le même état final.
  • Versionné — le code IaC suit Git, revue de code possible.
  • Reproductible — recréer un environnement identique en un clic.
Exemple Terraform — AWS EC2 
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "eu-west-3"
}

resource "aws_instance" "app" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t2.micro"

  tags = { Name = "devops-app" }
}

IaC dans le pipeline DevOps

Le code Terraform est intégré dans la CI/CD : terraform plan dans la PR, terraform apply automatique après merge sur main. L'état (state) est stocké dans un backend distant (S3, Terraform Cloud) pour le partage en équipe.

📖 Les concepts en détail

Avant l'IaC, l'infrastructure était configurée manuellement via SSH ou des interfaces web (console AWS, vSphere). Résultat : config drift, serveurs « snowflake » (chacun unique, impossible à reproduire), et changements non documentés.

L'IaC résout cela avec quatre piliers :

  • Déclaratif : vous décrivez l'état désiré, l'outil calcule le plan pour y parvenir. Exemple : Terraform lit le state existant, le compare à votre configuration, et génère un plan (terraform plan).
  • Idempotence : exécuter plusieurs fois le même code produit le même résultat. Si la ressource existe déjà, Terraform ne fait rien.
  • Push vs Pull : Ansible (push) se connecte aux machines et exécute des modules. Terraform (pull) interroge l'API du cloud et applique les différences. Chef/Puppet (pull) utilisent un agent sur chaque machine.
  • State management : l'état réel de l'infrastructure est stocké dans un fichier state. En équipe, il doit être partagé via un backend distant (S3, Azure Storage, Terraform Cloud) avec verrouillage (state lock).

⚠️ Pièges à éviter

State Lock oublié → corruption du state
Sans verrouillage, deux membres d'équipe peuvent appliquer simultanément, ce qui corrompt le fichier state. Utilisez un backend distant avec locking (DynamoDB pour S3, Terraform Cloud).
Drift de configuration non détecté
Une modification manuelle dans la console AWS désynchronise le state du réel. terraform plan détecte le drift. Automatisez son exécution régulière dans une pipeline CI.
Secrets en clair dans les fichiers .tf
Un mot de passe commité dans le dépôt est exposé à toute l'équipe et dans l'historique Git. Utilisez variables + fichiers .tfvars non commités, ou un gestionnaire de secrets (Vault, AWS Secrets Manager).
Modules non versionnés → régression
Un module Terraform qui change sans versionnement peut casser l'infrastructure du jour au lendemain. Référencez toujours une version (version = "~> 1.2") pour les modules du registry.

Scénario : L'équipe Ops provisionne un environnement de staging avec Terraform sur AWS.

  1. Le code Terraform est organisé en modules : vpc, ec2, rds, alb. Chaque module a ses propres variables et outputs.
  2. Le backend S3 + DynamoDB stocke le state avec verrouillage. Les fichiers .tfvars sont différents par environnement (dev, staging, prod).
  3. À chaque PR modifiant le dossier terraform/, une pipeline CI exécute terraform fmt -check, tflint et terraform plan. Le plan est commenté dans la PR.
  4. Après merge sur main, une pipeline CD exécute terraform apply -auto-approve pour déployer le changement.
  5. Un pipeline hebdomadaire exécute terraform plan pour détecter le drift et notifie l'équipe si une différence est trouvée.

Kubernetes K8s & Docker

Kubernetes (K8s) est un orchestrateur de conteneurs open-source qui automatise le déploiement, le scaling et la gestion d'applications conteneurisées. C'est le standard de facto de l'industrie pour les architectures microservices.

📦 Pod

Plus petite unité déployable. Un ou plusieurs conteneurs partageant le même réseau et stockage.

🔄 Deployment

Garantit un nombre de réplicas, gère les rolling updates et les rollbacks.

🌐 Service

Point d'entrée réseau stable vers un ensemble de Pods. Load-balancing intégré.

🚪 Ingress

Routage HTTP/HTTPS externe vers les Services. TLS, virtual hosting, rules.

Exemple de déploiement — API Node.js 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: registry.example.com/api:v1.2.3
          ports:
            - containerPort: 3000
          resources:
            limits:
              memory: 256Mi
              cpu: 200m
            requests:
              memory: 128Mi
              cpu: 100m
          livenessProbe:
            httpGet:
              path: /health
              port: 3000

📖 Les concepts en détail

Kubernete s'est imposé car il résout des problèmes concrets de la conteneurisation à grande échelle :

  • Auto-healing : si un Pod crash, le contrôleur en recrée un automatiquement pour respecter le nombre de réplicas défini.
  • Scaling : horizontal (plus de Pods) ou vertical (plus de ressources). Le Horizontal Pod Autoscaler (HPA) ajuste le nombre de réplicas selon la charge CPU/mémoire ou des métriques custom.
  • Rolling update : mise à jour progressive des Pods sans temps d'arrêt. En cas d'échec, kubectl rollout undo annule la mise à jour.
  • Configuration & Secrets : les ConfigMaps stockent la configuration non sensible (variables d'env, fichiers), les Secrets stockent les données sensibles (clés, tokens).
  • Stockage : les PersistentVolumes (PV) et PersistentVolumeClaims (PVC) abstraient le stockage physique (EBS, NFS, GCE PD) pour les applications stateful (bases de données).
  • Helm : gestionnaire de paquets K8s. Un chart Helm empaquette tous les manifests YAML d'une application avec des templates paramétrables.

⚠️ Pièges à éviter

Absence de resource limits → un Pod tue le Node
Sans resources.limits, un Pod peut consommer toute la mémoire du Node et faire planter les autres Pods. Définissez toujours des requests et limits pour CPU et mémoire.
Image tag :latest → déploiement non reproductible
image: myapp:latest change à chaque build. On ne peut pas savoir quelle version tourne, ni revenir en arrière. Utilisez un tag sémantique (v1.2.3) ou le hash du commit.
RBAC trop permissif → risque de sécurité
Un ServiceAccount avec des droits admin octroie un accès total au cluster. Appliquez le principe du moindre privilège avec des Roles et RoleBindings spécifiques par namespace.
ConfigMap modifiée → Pod non rechargé
Modifier une ConfigMap ne redémarre pas automatiquement les Pods. Utilisez un outil comme Reloader ou montez la ConfigMap en volume pour un rechargement à chaud.

📚 Lexique

Deployment Ressource qui gère un ensemble de réplicas de Pods avec rolling update, rollback et scaling déclaratif.
Service Abstraction réseau qui expose un ensemble de Pods via une IP stable et un nom DNS, avec load-balancing intégré.

💡 Exemple concret

Scénario : L'équipe déploie une API Node.js avec une base PostgreSQL sur un cluster K8s en Minikube (développement local).

  1. L'API est conteneurisée dans une image Docker taguée api:v1.0.0 et poussée sur un registry.
  2. Un fichier deployment.yaml définit 3 réplicas avec une sonde de santé (livenessProbe) et des resource limits.
  3. Un service.yaml expose les Pods sur le port 80 en ClusterIP (interne au cluster).
  4. Un ingress.yaml route api.monapp.com vers le Service avec terminaison TLS gérée par cert-manager.
  5. PostgreSQL est déployé via un StatefulSet avec un PersistentVolumeClaim pour les données, référencé via un Secret pour le mot de passe.
  6. La pipeline CI/CD construit l'image, met à jour le tag dans le fichier YAML et exécute kubectl apply -f k8s/ pour déployer.

🧠 Quiz express

1. Quel objet Kubernetes garantit un nombre défini de réplicas de Pods ?

  • Service
  • Deployment
  • Ingress
  • ConfigMap

Un Deployment gère le cycle de vie des Pods : il maintient le nombre de réplicas, exécute les rolling updates et permet le rollback. Le Service ne fait que du routage réseau.

2. À quoi sert un objet Ingress dans Kubernetes ?

  • Stocker des mots de passe
  • Créer des volumes persistants
  • Exposer des Services HTTP/HTTPS vers l'extérieur avec routage et TLS
  • Définir le nombre de réplicas

Un Ingress expose vos Services à l'extérieur du cluster avec des règles de routage par hostname/chemin et la terminaison TLS. Sans Ingress, les Services ne sont accessibles qu'en interne (ClusterIP) ou via un LoadBalancer.

3. Pourquoi ne faut-il pas utiliser le tag :latest pour les images en production ?

  • C'est plus lent à télécharger
  • Le tag change à chaque build, rendant le déploiement non reproductible et le rollback impossible
  • Kubernetes ne supporte pas :latest
  • Cela consomme plus de mémoire

Avec :latest, on ne sait pas quelle version du code tourne réellement, et on ne peut pas revenir à la version précédente. Toujours utiliser un tag sémantique (v1.2.3) ou le hash du commit (a1b2c3d).

🧪 Travaux pratiques — Déployer Nginx sur Kubernetes avec rolling update

Utilisez Killercoda (gratuit, sans installation, recommandé par kubernetes.io) qui fournit un cluster Kubernetes pré-initialisé prêt à l'emploi. Connectez-vous avec un compte GitHub ou Google.

  1. Ouvrez killercoda.com/playgrounds/scenario/kubernetes et cliquez sur Start. Choisissez l'image kubernetes-kubeadm-1node. ⏳ La session dure 1 heure (gratuit, 4h avec compte PLUS).
  2. Vérifiez que le cluster est opérationnel : kubectl get nodes → un nœud Ready s'affiche.
  3. Déployez Nginx : kubectl create deployment hello-nginx --image=nginx:1.25.
  4. Exposez le déploiement : kubectl expose deployment hello-nginx --port=80 --type=NodePort.
  5. Montez à 3 réplicas : kubectl scale deployment hello-nginx --replicas=3 → kubectl get pods -w.
  6. Faites un rolling update : kubectl set image deployment/hello-nginx nginx=nginx:1.26 → kubectl rollout status deployment/hello-nginx. Lancez kubectl get pods -w & avant la commande pour voir les pods se remplacer un par un en temps réel.
  7. Annulez le déploiement : kubectl rollout undo deployment/hello-nginx → vérifiez l'historique avec kubectl rollout history deployment/hello-nginx.
  8. Vérifiez l'accès : kubectl get svc hello-nginx → notez le port 3xxxx (colonne PORT(S)). Testez depuis le terminal : curl http://localhost:3xxxx (remplacez 3xxxx).

3. Comprendre GitHub Actions — les concepts clés

GitHub Actions est le moteur CI/CD intégré à GitHub. Voici son vocabulaire essentiel :

Workflow Fichier YAML (dans .github/workflows/) qui définit une ou plusieurs automatisations.
Event Déclencheur : push, pull_request, schedule (cron), workflow_dispatch (manuel), etc.
Job Ensemble d'étapes exécutées sur le même runner. Les jobs peuvent s'exécuter en parallèle ou en séquence.
Step Action unitaire : une commande shell ou une action réutilisable (ex: actions/checkout@v6).
Runner (GitHub-hosted) Machine virtuelle gérée par GitHub (Ubuntu, Windows, macOS). Zéro configuration — vous écrivez juste runs-on: ubuntu-latest et GitHub fournit la machine gratuitement (dans la limite du quota Free). C'est ce que nous utilisons.
Runner (Self-hosted) Votre propre machine (serveur local, VM, Raspberry Pi) que vous connectez à GitHub via l'onglet Settings → Actions → Runners. Utile si vous avez besoin de matériel spécifique ou dépassez le quota gratuit. N'est pas requis pour ce projet.
Action Brique réutilisable publiée sur le GitHub Marketplace. Exemple : actions/checkout@v6 clone le dépôt.
Artifact Fichier produit par un job (ex: le dossier du site compilé) et passé au job suivant ou téléchargé.
Secret Variable chiffrée stockée dans le dépôt (Settings → Secrets and variables). Ne jamais hard-coder un token.

4. Activer GitHub Pages — choisir la source « GitHub Actions »

GitHub Pages propose deux modes de publication. Il est essentiel de comprendre leur différence pour choisir le bon dans le cadre d'une démo CI/CD.

🔹 Mode A — Deploy from a branch (simplifié, pas de CI/CD)

GitHub déploie directement le contenu d'une branche (ex: main) sans pipeline. Simple, mais aucune CI/CD à montrer. Le site est mis à jour automatiquement à chaque push, mais il n'y a ni test, ni build, ni visibilité sur le processus.

🔹 Mode B — GitHub Actions (recommandé pour la démo — celui que nous utilisons)

Vous écrivez un workflow YAML qui contrôle exactement quand et comment le site est construit et déployé. C'est la véritable CI/CD que les étudiants doivent apprendre. Chaque exécution est tracée dans l'onglet Actions avec logs détaillés.

Procédure pour choisir le mode GitHub Actions

  1. Ouvrez votre dépôt sur GitHub.
  2. Allez dans l'onglet Settings (le dernier en haut à droite).
  3. Dans le menu latéral gauche, cliquez sur Pages.
  4. Sous « Build and deployment », dans la liste déroulante Source, sélectionnez GitHub Actions.
    Ne choisissez pas « Deploy from a branch » — cela contournerait la pipeline CI/CD.
  5. GitHub vous propose alors des templates de workflow. Cliquez sur Cancel ou fermez la suggestion : nous allons écrire notre propre workflow à l'étape suivante.

📌 Ce qui change avec le mode « GitHub Actions »

GitHub ne déploie plus automatiquement le contenu de la branche. Il attend qu'un workflow (via actions/deploy-pages) publie le site. Sans workflow, le site reste inactif. L'environnement de déploiement github-pages est créé automatiquement lors de la première run. C'est exactement ce que nous voulons : le pipeline contrôle le déploiement, pas GitHub automatiquement.

5. Créer le workflow CI/CD avec GitHub Actions

Le fichier YAML ci-dessous définit un workflow qui se déclenche à chaque push sur la branche main. Il utilise les actions officielles GitHub pour préparer et déployer le site sur Pages.

Création via l'interface GitHub (recommandé pour les débutants)

  1. Sur la page d'accueil de votre dépôt, cliquez sur Add file → Create new file.
  2. Dans le champ « Name your file... », tapez exactement : .github/workflows/deploy.yml.
    Respectez l'emplacement et le nom — le dossier doit être .github/workflows/ (avec un s).
  3. Copiez le contenu YAML ci-dessous et collez-le dans l'éditeur en ligne.
  4. Cliquez sur Commit changes... → validez directement sur main.

⚠️ Condition impérative pour voir le workflow dans Actions

Le fichier YAML doit se trouver sur la branche par défaut du dépôt (généralement main). Si vous créez le fichier sur une branche feature, le workflow n'apparaît pas dans l'onglet Actions tant qu'il n'est pas fusionné sur main. Validez directement sur main ou mergez-y la branche avant de chercher le workflow.

Variante locale : créez le dossier .github/workflows/ à la racine du projet, placez-y le fichier, puis git add .github/ && git commit -m "ci: ajout du workflow Pages" && git push. Assurez-vous de pousser sur la branche main.

.github/workflows/deploy.yml 
# Nom du workflow (apparaît dans l'onglet Actions)
name: Deploy to GitHub Pages

# Déclencheur : s'exécute à chaque push sur main
on:
  push:
    branches:
      - main

  # Permet aussi un déclenchement manuel depuis l'UI GitHub
  workflow_dispatch:

# Un seul job : "deploy" (d'autres jobs CI pourraient être ajoutés)
jobs:
  deploy:
    # Runner : machine Ubuntu fournie gratuitement par GitHub
    runs-on: ubuntu-latest

    # Permissions nécessaires pour déployer sur Pages
    permissions:
      contents: read
      pages: write
      id-token: write

    # Environnement de déploiement (historise les déploiements)
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    # Les 4 étapes de la pipeline
    steps:
      # 1. Récupère le code source du dépôt
      - name: Checkout repository
        uses: actions/checkout@v6

      # 2. Configure l'environnement GitHub Pages
      - name: Setup Pages
        uses: actions/configure-pages@v6

      # 3. Empaquette tous les fichiers du site en un artifact
      - name: Upload artifact
        uses: actions/upload-pages-artifact@v5
        with:
          path: '.'

      # 4. Déploie l'artifact sur GitHub Pages
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v5

🔍 Que fait chaque action ?

  • actions/checkout@v6 — Clone le dépôt sur le runner (comme un git clone).
  • actions/configure-pages@v6 — Détecte la configuration Pages du dépôt et prépare le runner.
  • actions/upload-pages-artifact@v5 — Compresse le dossier spécifié (path: '.') en un artifact uploadé sur GitHub.
  • actions/deploy-pages@v5 — Prend l'artifact et le publie sur l'infrastructure GitHub Pages (CDN mondiale).

10. Dépannage — problèmes courants

❌ Le workflow n'apparaît pas dans l'onglet Actions

C'est le problème le plus fréquent. Causes possibles :

  1. Mauvaise branche — Le fichier doit être sur la branche par défaut (généralement main). S'il est sur une branche feature, il n'apparaît pas. Mergez-le ou recréez-le sur main.
  2. Mauvais chemin — Le fichier doit être exactement à .github/workflows/deploy.yml (avec un s à workflows, et l'extension .yml).
  3. Erreur YAML — Une erreur de syntaxe dans le fichier empêche GitHub de le lire. Vérifiez l'indentation (2 espaces).
  4. Actions désactivé — Vérifiez dans Settings → Actions → General que « Allow all actions » est coché.
  5. Source Pages mal configurée — Retournez dans Settings → Pages et vérifiez que la source est bien GitHub Actions (pas « Deploy from a branch »).
❌ Aucun runner affiché dans Settings → Actions → Runners

Ce n'est pas une erreur, c'est normal sur un compte Free. La page « Runners » sert uniquement à configurer des self-hosted runners (vos propres machines). Notre workflow utilise runs-on: ubuntu-latest qui fait appel aux runners GitHub-hosted — des machines gérées par GitHub, gratuites et sans aucune configuration.

Pour vérifier que les runners GitHub-hosted fonctionnent : lancez une exécution du workflow (via un push sur main ou le bouton Run workflow dans l'onglet Actions). Les logs montreront « Job is running on ubuntu-latest » — c'est la preuve que le runner GitHub-hosted est actif. Vous n'avez rien à configurer dans la section Runners.

❌ La run Actions échoue avec « Error: No uploaded artifact was found »

Vérifiez que le paramètre path dans l'étape upload-pages-artifact pointe vers le bon dossier. Pour ce projet, utilisez path: '.' (tout le dépôt).

❌ Le site affiche une page blanche ou une erreur 404
  1. Vérifiez que le fichier index.html est bien à la racine du dépôt.
  2. Assurez-vous que GitHub Pages est activé (Settings → Pages) avec la source GitHub Actions (pas « Deploy from a branch »).
  3. Si l'URL est https://user.github.io/devops-academy/ et que le site appelle des ressources en relatif, vérifiez les chemins (ils doivent être relatifs).
  4. Patientez 1 à 2 minutes après le déploiement — le cache CDN peut prendre un peu de temps.
❌ « Permission denied » ou « Resource not accessible by integration »

Votre workflow doit déclarer les permissions suivantes dans le job :

permissions:
  contents: read
  pages: write
  id-token: write

Ces permissions sont déjà présentes dans le fichier YAML fourni.

❌ Mon push ne déclenche pas la pipeline
  1. Vérifiez que le fichier est bien nommé .github/workflows/deploy.yml (attention au s à workflows).
  2. Vérifiez que l'événement on: push: branches: [main] correspond à la branche sur laquelle vous poussez.
  3. Vérifiez que la source Pages est sur GitHub Actions et non « Deploy from a branch ».
  4. Allez dans l'onglet Actions : si le workflow n'apparaît pas du tout, cliquez sur le sélecteur de workflow à gauche (ou « New workflow ») et cherchez-y « Deploy to GitHub Pages ».
❌ Je dépasse le quota gratuit de minutes Actions

GitHub désactive automatiquement les workflows pour le reste du mois. Pour réduire la consommation :

  • Évitez les pushes inutiles sur main.
  • Utilisez un runner auto-hébergé si vous avez une machine disponible.
  • Passez à un plan Team (4 $/mois) ou utilisez le Student Pack.
