Bienvenue dans l'univers DevOps

Le DevOps est bien plus qu'un ensemble d'outils : c'est une culture qui rapproche les équipes de développement (Dev) et d'exploitation (Ops) pour livrer des logiciels de qualité plus rapidement et de manière plus fiable.

🤝

Collaboration

Fin des silos entre Dev et Ops. Les équipes partagent la responsabilité du cycle de vie complet de l'application.

⚡

Automatisation

Build, test, déploiement : tout ce qui peut être automatisé doit l'être, afin d'éliminer les erreurs manuelles et accélérer les livraisons.

📊

Mesure

Des métriques précises (MTTR, déploiements par jour, taux d'échec) guident l'amélioration continue.

🔄

Amélioration Continue

Chaque incident est une opportunité d'apprentissage. Les processus évoluent par rétroaction constante.

Bénéfices pour l'entreprise

  • Réduction du Time-to-Market – livraisons plus fréquentes et plus sûres.
  • Qualité logicielle accrue – tests automatisés et intégration continue.
  • Meilleure résilience – déploiements progressifs, rollbacks rapides.
  • Satisfaction clients – fonctionnalités livrées en continu, feedback immédiat.

Planification Plan

La planification DevOps s'appuie sur les principes Agile et Lean pour prioriser le travail, gérer les dépendances et suivre l'avancement en temps réel.

Méthodes Agiles

  • Scrum – Sprints (1–4 semaines), daily stand-ups, rétrospectives.
  • Kanban – Flux continu, limite du travail en cours (WIP), visibilité totale.
  • SAFe – Mise à l'échelle Agile pour les grandes organisations.

Outils de suivi

  • GitHub Issues / Projects – Tableaux Kanban intégrés au code.
  • Jira – Roadmaps, epic, user stories, backlog.
  • Confluence – Documentation collaborative des décisions.

📌 Le saviez-vous ?

Les équipes DevOps matures utilisent des « Service Level Objectives » (SLO) pour définir des objectifs de fiabilité dès la phase de planification.

Développement Code

Le code est le cœur du logiciel. Une gestion rigoureuse des versions et des processus de code review est indispensable.

Git & Stratégies de branching

  • Git Flow – Branches main, develop, feature/*, release/*, hotfix/*.
  • Trunk-based – Branches courtes, intégration multiple fois par jour.
  • GitHub Flow – main + branches de fonctionnalités, PR obligatoire.

Bonnes pratiques

  • Commits atomiques et messages explicites (conventional commits).
  • Code review systématique via Pull Request.
  • Protection de branche avec – vérifications obligatoires avant merge.
Exemple de conventional commit 
feat(api): ajouter le endpoint de création d'utilisateur
fix(auth): corriger le token expiré en session
docs(readme): mettre à jour les instructions d'installation

Intégration Continue Build & Test

L'Intégration Continue (CI) consiste à fusionner le travail des développeurs plusieurs fois par jour et à valider chaque changement par des tests automatisés.

🔍 Build automatisé

Compilation, résolution des dépendances, analyse statique (linting).

✅ Tests unitaires

Valident chaque fonction individuellement. Exécutés à chaque commit.

🧪 Tests d'intégration

Vérifient les interactions entre composants (API, base de données).

📈 Qualité du code

SonarQube, CodeQL, couverture de code – seuils de qualité bloquants.

Pratique recommandée

Chaque Pull Request doit passer une pipeline CI complète avant d'être mergée. La branche main doit toujours être déployable.

Déploiement Continu Release & Deploy

Le Continuous Deployment (CD) automatise la mise en production de chaque changement validé par la CI, sans intervention manuelle.

Stratégies de déploiement

🟢 Blue/Green

Deux environnements identiques. Bascule instantanée du trafic de Blue (actuel) vers Green (nouveau). Rollback immédiat.

🐤 Canary

Nouvelle version déployée pour un faible % d'utilisateurs. Surveillance avant extension progressive.

🌊 Rolling update

Remplacement progressif des instances une par une (ou par lots). Aucun temps d'arrêt.

🐳 Conteneurisation

Docker empaquette l'application et ses dépendances. Image immuable, identique en dev, test et prod.

Exemple Dockerfile 
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80

Monitoring & Feedback Observabilité

L'observabilité repose sur trois piliers : logs, métriques et traces. Elle permet de comprendre l'état interne d'un système en production.

📜 Logs

Événements textuels horodatés. Outils : ELK Stack (Elasticsearch, Logstash, Kibana), Loki, CloudWatch.

📊 Métriques

Données numériques agrégées (CPU, mémoire, requêtes/s). Outils : Prometheus, Grafana, Datadog.

🔗 Tracing

Suivi d'une requête à travers tous les services (APM). Outils : Jaeger, OpenTelemetry, New Relic.

🔄 Boucle de rétroaction

Les alertes remontent aux équipes Dev via Slack/PagerDuty. Les post-mortems alimentent le backlog d'amélioration.

Ce guide détaille chaque étape pour transformer ces fichiers statiques en un site livré en continu via GitHub Actions sur GitHub Pages, le tout sur un compte gratuit.

2. Créer le dépôt sur GitHub

Méthode A — Créer le dépôt puis pousser le code en local

  1. Cliquez sur le + en haut à droite de GitHub → New repository.
  2. Nommez-le devops-academy (ou le nom de votre choix).
  3. Cochez Public (nécessaire pour GitHub Pages gratuit).
  4. Ne cochez pas « Add a README » (nous allons pousser le projet existant).
  5. Cliquez sur Create repository.

Dans votre terminal, à la racine du projet, exécutez :

git init
git add .
git commit -m "feat: première version de l'application DevOps Academy"
git remote add origin https://github.com/votre-utilisateur/devops-academy.git
git push -u origin main

Méthode B — Tout faire depuis l'interface web de GitHub

  1. Créez le dépôt avec le même nom, mais cette fois cochez « Add a README ».
  2. Dans le dépôt, cliquez sur Add file → Upload files.
  3. Glissez-déposez les fichiers index.html, styles.css et app.js.
  4. Ajoutez un message de commit et validez.

⚠️ Important

Pour la démonstration DevOps, la Méthode A est préférable : elle vous fait manipuler Git en ligne de commande, ce qui est une compétence fondamentale en entreprise.

3. Comprendre GitHub Actions — les concepts clés

GitHub Actions est le moteur CI/CD intégré à GitHub. Voici son vocabulaire essentiel :

Workflow Fichier YAML (dans .github/workflows/) qui définit une ou plusieurs automatisations.
Event Déclencheur : push, pull_request, schedule (cron), workflow_dispatch (manuel), etc.
Job Ensemble d'étapes exécutées sur le même runner. Les jobs peuvent s'exécuter en parallèle ou en séquence.
Step Action unitaire : une commande shell ou une action réutilisable (ex: actions/checkout@v4).
Runner Machine virtuelle (Ubuntu, Windows, macOS) qui exécute le job. Les runners hébergés par GitHub sont gratuits (limités).
Action Brique réutilisable publiée sur le GitHub Marketplace. Exemple : actions/checkout@v4 clone le dépôt.
Artifact Fichier produit par un job (ex: le dossier du site compilé) et passé au job suivant ou téléchargé.
Secret Variable chiffrée stockée dans le dépôt (Settings → Secrets and variables). Ne jamais hard-coder un token.

4. Activer GitHub Pages dans les paramètres

GitHub Pages permet d'héberger un site statique directement depuis un dépôt. Voici la procédure :

  1. Ouvrez votre dépôt sur GitHub.
  2. Allez dans l'onglet Settings (le dernier en haut à droite).
  3. Dans le menu latéral gauche, cliquez sur Pages.
  4. Sous « Branch », sélectionnez main et le dossier / (root).
  5. Cliquez sur Save.
  6. Après quelques secondes, le message « Your site is live at https://votre-utilisateur.github.io/devops-academy/ » apparaît en haut de la page.

📌 Ce qui se passe en coulisses

Quand vous sélectionnez une branche, GitHub déploie automatiquement le contenu du dossier racine de cette branche sur ses serveurs statiques (CDN). Cependant, sans GitHub Actions, il n'y a pas de pipeline CI/CD — le déploiement est automatique mais non industrialisé. L'étape suivante ajoute la véritable chaîne CI/CD.

5. Créer le workflow CI/CD avec GitHub Actions

Le fichier YAML ci-dessous définit un workflow qui se déclenche à chaque push sur la branche main. Il utilise les actions officielles GitHub pour préparer et déployer le site sur Pages.

Création via l'interface GitHub (recommandé pour les débutants)

  1. Sur la page d'accueil de votre dépôt, cliquez sur Add file → Create new file.
  2. Dans le champ « Name your file... », tapez exactement : .github/workflows/deploy.yml.
  3. Copiez le contenu YAML ci-dessous et collez-le dans l'éditeur en ligne.
  4. Cliquez sur Commit changes... → validez directement sur main.

Variante locale : créez le dossier .github/workflows/ à la racine du projet, placez-y le fichier, puis git add && git commit && git push.

.github/workflows/deploy.yml 
# Nom du workflow (apparaît dans l'onglet Actions)
name: Deploy to GitHub Pages

# Déclencheur : s'exécute à chaque push sur main
on:
  push:
    branches:
      - main

  # Permet aussi un déclenchement manuel depuis l'UI GitHub
  workflow_dispatch:

# Un seul job : "deploy" (d'autres jobs CI pourraient être ajoutés)
jobs:
  deploy:
    # Runner : machine Ubuntu fournie gratuitement par GitHub
    runs-on: ubuntu-latest

    # Permissions nécessaires pour déployer sur Pages
    permissions:
      contents: read
      pages: write
      id-token: write

    # Environnement de déploiement (historise les déploiements)
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}

    # Les 4 étapes de la pipeline
    steps:
      # 1. Récupère le code source du dépôt
      - name: Checkout repository
        uses: actions/checkout@v4

      # 2. Configure l'environnement GitHub Pages
      - name: Setup Pages
        uses: actions/configure-pages@v4

      # 3. Empaquette tous les fichiers du site en un artifact
      - name: Upload artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: '.'

      # 4. Déploie l'artifact sur GitHub Pages
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4

🔍 Que fait chaque action ?

  • actions/checkout@v4 — Clone le dépôt sur le runner (comme un git clone).
  • actions/configure-pages@v4 — Détecte la configuration Pages du dépôt et prépare le runner.
  • actions/upload-pages-artifact@v3 — Compresse le dossier spécifié (path: '.') en un artifact uploadé sur GitHub.
  • actions/deploy-pages@v4 — Prend l'artifact et le publie sur l'infrastructure GitHub Pages (CDN mondiale).

6. Déclencher la pipeline et suivre son exécution

  1. Après avoir commité le fichier deploy.yml, GitHub détecte automatiquement le nouveau workflow.
  2. Allez dans l'onglet Actions de votre dépôt. Vous y voyez une liste des workflow runs.
  3. Cliquez sur la run en cours (cercle jaune) pour voir les logs en temps réel — chaque étape est affichée avec son statut (✅ succès, ❌ échec).
  4. En fin d'exécution, le cercle devient vert ✅ (succès) ou rouge ❌ (échec).

À quoi ressemble un run ? Cliquez sur Simuler ci-dessous pour voir l'ordre des étapes.

7. Vérifier le déploiement en ligne

  1. Une fois la pipeline terminée (✅), retournez dans Settings → Pages.
  2. En haut de la page, un message vert indique : « Your site is live at https://votre-utilisateur.github.io/devops-academy/ ».
  3. Cliquez sur le lien ou ouvrez-le dans un nouvel onglet.
  4. Vous devriez voir exactement le même contenu que sur votre machine locale.

📌 À savoir

La première exécution peut prendre 1 à 2 minutes (téléchargement des actions, upload, propagation CDN). Les runs suivants sont plus rapides car les actions sont mises en cache.

8. Le cycle DevOps complet — modifier et redéployer

La puissance du DevOps, c'est le cycle itératif. Essayez :

  1. Modifiez un fichier localement (par exemple changez le titre dans index.html).
  2. Commitez et poussez : 
    git add index.html
git commit -m "feat: mettre à jour le titre de l'accueil"
git push
  3. Allez dans l'onglet Actions — une nouvelle run démarre automatiquement.
  4. Une fois la run terminée, rafraîchissez le site : le changement est en ligne.

🔁 C'est ça, le Continuous Deployment !

Chaque commit sur main est automatiquement intégré (CI) et déployé (CD) sans intervention humaine. En entreprise, on ajoute des tests automatisés dans la pipeline pour valider le code avant déploiement.

9. Plan gratuit — limites et comment les surveiller

Le plan Free de GitHub est généreux mais pas illimité. Voici ce qu'il faut surveiller :

Ressource Limite Free Consommation estimée pour ce projet
Minutes GitHub Actions / mois 2 000 min ~30 sec par run → ~1 200 runs/mois
Stockage des artefacts 500 Mo ~50 Ko par artifact → négligeable

⚠️ Bien régler le comportement du workflow

Si vous poussez 50 fois par jour sur main, vous consommerez environ 25 minutes/mois — bien en dessous du quota. Évitez de déclencher la pipeline sur des branches de travail (feature) inutilement ; utilisez on: push: branches: [main] comme dans l'exemple.

10. Dépannage — problèmes courants

❌ La run Actions échoue avec « Error: No uploaded artifact was found »

Vérifiez que le paramètre path dans l'étape upload-pages-artifact pointe vers le bon dossier. Pour ce projet, utilisez path: '.' (tout le dépôt).

❌ Le site affiche une page blanche ou une erreur 404
  1. Vérifiez que le fichier index.html est bien à la racine du dépôt.
  2. Assurez-vous que GitHub Pages est activé (Settings → Pages) sur la branche main, dossier / (root).
  3. Si l'URL est https://user.github.io/devops-academy/ et que le site appelle des ressources en relatif, vérifiez les chemins (ils doivent être relatifs).
  4. Patientez 1 à 2 minutes après le déploiement — le cache CDN peut prendre un peu de temps.
❌ « Permission denied » ou « Resource not accessible by integration »

Votre workflow doit déclarer les permissions suivantes dans le job :

permissions:
  contents: read
  pages: write
  id-token: write

Ces permissions sont déjà présentes dans le fichier YAML fourni.

❌ Mon push ne déclenche pas la pipeline
  1. Vérifiez que le fichier est bien nommé .github/workflows/deploy.yml (attention au s à workflows).
  2. Vérifiez que l'événement on: push: branches: [main] correspond à la branche sur laquelle vous poussez.
  3. Allez dans l'onglet Actions : si le workflow n'apparaît pas du tout, cliquez sur « New workflow » → cherchez votre fichier YAML dans la liste.
❌ Je dépasse le quota gratuit de minutes Actions

GitHub désactive automatiquement les workflows pour le reste du mois. Pour réduire la consommation :

  • Évitez les pushes inutiles sur main.
  • Utilisez un runner auto-hébergé si vous avez une machine disponible.
  • Passez à un plan Team (4 $/mois) ou utilisez le Student Pack.
